DÉBUT DU PROJET · avant mai 2026 Genèse — Pourquoi Derush Tool ? Architecture

Le point de départ est un problème concret : lors des tournages du projet DRIFT_CLUB, plusieurs personnes (Sébastien, Paola, et d'autres) doivent visualiser les rushs, les noter, poser des marqueurs et synchroniser leur travail. Les outils existants sont soit trop lourds (DaVinci Resolve au complet juste pour annoter), soit pas adaptés au travail collaboratif sur des fichiers locaux.

Le besoin : un outil léger qui tourne en local sur n'importe quel PC, qui ne nécessite pas d'abonnement cloud, et qui permet à plusieurs personnes de travailler sur les mêmes rushs — certains au même endroit sur un réseau local, d'autres depuis chez eux via une sync internet.

Contraintes du terrain

  • Les rushs sont sur des disques durs physiques — pas dans le cloud. Chaque collaborateur a potentiellement les fichiers dans un dossier différent sur sa machine.
  • Les fichiers Sony FX6 sont en MXF — format non lisible directement dans un navigateur web.
  • Il faut pouvoir exporter vers DaVinci Resolve avec les marqueurs et les selects.
  • L'outil doit être distribuable sans installation complexe (pas de Python requis sur les machines des collaborateurs).
FONDATIONS Architecture — Un serveur Python, une interface HTML Architecture

La décision architecturale fondamentale : un serveur HTTP local en Python qui expose une API REST, avec une interface web HTML/JS monofichier qui s'ouvre dans le navigateur. C'est ce couple qui permet à la fois la richesse d'une vraie interface et la simplicité du déploiement.

Pourquoi ce choix ?

  • Python : accès facile à ffmpeg (subprocess), manipulation de fichiers, génération de formats comme FCPXML et EDL. Aucune dépendance réseau externe à gérer.
  • Navigateur comme rendu : HTML/CSS/JS donnent une interface riche sans framework lourd. Le navigateur gère déjà la lecture vidéo, le canvas pour les dessins, les timelines CSS.
  • Monofichier HTML : un seul fichier derush_app.html bundlé dans l'exe. Pas de serveur de fichiers complexe, pas de build frontend.
  • PyInstaller : transforme le tout en un DerushTool.exe autonome — double-cliquer suffit.

La subtilité PyInstaller : APP_DIR vs BUNDLE_DIR

Quand PyInstaller crée l'exe, les fichiers embarqués (HTML, images) sont extraits dans un dossier temporaire _MEIPASS à chaque lancement. Les données utilisateur (projets, config, profil) doivent être ailleurs — dans %APPDATA%\DerushTool\ — pour persister entre les mises à jour.

Piège : servir derush_app.html depuis APP_DIR (à côté de l'exe) au lieu de BUNDLE_DIR (_MEIPASS) faisait que le HTML était introuvable dans l'exe packagé. Ce bug a été découvert lors du premier vrai test sur une autre machine.

Le streaming vidéo MXF

Les fichiers MXF ne se lisent pas dans un navigateur natif. La solution : l'endpoint /proxy/<rel_path> qui streame le fichier en chunks avec support du Range HTTP (pour que le navigateur puisse seeker dans la vidéo sans tout télécharger). Quand un proxy MP4 existe dans Sub/Proxy/, il est préféré pour la fluidité.

FONDATIONS Scanner les rushs — détection caméra et timecode Feature

Le scan est le cœur du système. Il parcourt récursivement un dossier et construit la liste des clips avec leurs métadonnées. La principale complexité est que chaque caméra stocke ses informations différemment.

Source de timecode Sony FX6

La FX6 enregistre en MXF avec un timecode embarqué, mais ffprobe retourne parfois les bytes dans le mauvais ordre (endianness inversé). Un fix spécifique a été appliqué pour les fichiers FX6 : lecture des 4 bytes de TC et réorganisation. Ce fix est conditionnel — il ne s'applique qu'aux fichiers où FX6 est détecté dans le nom de caméra, pour ne pas casser d'autres formats.

Bug initial : Le fix byte-reversal s'appliquait à tous les fichiers dont le nom commençait par DRIFT_ — une convention du projet spécifique. Quand quelqu'un a testé avec des rushs d'une autre caméra dont les fichiers ne s'appelaient pas DRIFT_xxx, les timecodes étaient incorrects ou ignorés.
Fix : Condition basée sur le modèle de caméra détecté ('FX6' in camera.upper()), pas sur le nom de fichier.

Sidecar XML Sony

La FX6 génère un fichier XML à côté de chaque MXF avec les métadonnées techniques complètes (ISO, ouverture, angle d'obturation, focale). La fonction parse_sony_xml() les extrait et les associe au clip. Pour les autres caméras, on tente d'extraire ces mêmes infos depuis les tags ffprobe — chaque marque utilise des noms de tags différents, donc on essaie une liste de candidats dans l'ordre.

La détection du "jour de tournage"

L'arborescence DRIFT_CLUB était structurée comme J02_2026_xx_xx/IMAGE/FX6/.... Le scan extrayait le premier élément du chemin relatif pour identifier le jour. Mais si les rushs étaient directement à la racine du dossier (structure plate), la logique retournait le nom de fichier lui-même comme "jour" — ce qui créait des en-têtes absurdes dans l'interface.

Fix : day = parts[0] if len(parts) > 1 else '' — si le fichier est directement à la racine, il n'a pas de "jour".
FONDATIONS Système multi-utilisateurs — profils, sessions, invitations Architecture

Le modèle multi-utilisateurs a évolué plusieurs fois. À l'origine, les utilisateurs étaient définis uniquement dans le projet (avec un nom + un mot de passe hashé). Le problème : si deux projets coexistaient, chaque projet avait ses propres comptes — incohérent pour des gens qui travaillent sur plusieurs projets.

Système de profil global (un par machine)

La solution adoptée : chaque machine a un profil unique stocké dans %APPDATA%\DerushTool\derush_profile.json. Ce profil contient juste un identifiant et un mot de passe hashé. Quand on rejoint un projet, ce profil est vérifié contre la liste des utilisateurs autorisés dans le projet.

Système de clé d'invitation

Le flux pour ajouter un collaborateur est intentionnellement simple et sécurisé. L'admin génère une clé à 8 caractères (usage unique) associée à l'identifiant du collaborateur. Le collaborateur entre cette clé + l'ID du projet, et le système télécharge automatiquement le projet depuis le cloud. La clé est supprimée du projet après utilisation.

Subtilité : Le champ user_id dans les sessions est un alias de username — ajouté pour la compatibilité avec du code plus ancien qui utilisait id ou name comme clé. La fonction user_note_key() centralise cette résolution pour ne pas avoir à y penser partout.
FONDATIONS Sync cloud — le PHP sur sebastiendelahaye.be Architecture

Pour permettre à des collaborateurs distants de partager leurs annotations, on a choisi une solution minimaliste : un script PHP hébergé sur le propre serveur de Sébastien (sebastiendelahaye.be/derush_sync.php). Chaque projet est stocké comme un fichier JSON sur ce serveur. Pas de base de données, pas de service tiers, pas d'abonnement.

Stratégie de merge sans conflit

Le point critique : quand deux personnes ont travaillé en parallèle et que l'une sync, elle ne doit pas écraser le travail de l'autre. La solution repose sur le fait que chaque utilisateur n'écrit que ses propres notes dans l'objet notes[user_id]. Le merge consiste simplement à faire l'union des notes par user_id (local gagne pour ses propres notes), l'union des discussions par timestamp, et l'union des users par id.

Auto-sync en arrière-plan

Un thread daemon surveille la connexion réseau toutes les 90 secondes. Si la connexion est revenue après une coupure, il déclenche une sync automatique. Une sync toutes les 10 minutes est aussi assurée en permanence. L'interface affiche un dot coloré (vert/rouge/gris) pour l'état de sync.

FONDATIONS Build PyInstaller — les pièges du packaging Architecture

Transformer un script Python en exe autonome avec PyInstaller semble simple mais cache plusieurs pièges découverts un par un.

Piège 1 — UnboundLocalError sur threading

Python a une règle surprenante : si vous écrivez import threading n'importe où dans une fonction, Python traite threading comme une variable locale dans toute la fonction — même avant l'import. Si du code avant l'import essaie d'utiliser threading, on obtient un UnboundLocalError. Visible seulement dans l'exe (pas en dev) car PyInstaller modifie l'ordre d'initialisation des modules.

Piège 2 — Les fenêtres CMD qui flashent

Chaque appel subprocess.run() pour lancer ffmpeg ouvrait une fenêtre de terminal visible brièvement. Fix : creationflags=subprocess.CREATE_NO_WINDOW sur Windows.

Piège 3 — Le bouton Parcourir qui relançait l'exe entier

Pour ouvrir une fenêtre native de sélection de dossier, le premier réflexe était de lancer un sous-process Python avec sys.executable. Dans l'exe, sys.executable pointe sur DerushTool.exe lui-même — le lancer démarrait une deuxième instance complète du logiciel, avec ouverture du navigateur, etc. La solution correcte est d'utiliser tkinter directement dans le serveur via un thread, en retournant le résultat par une queue.

Solution finale pour tkinter

Thread séparé → tkinter.filedialog.askdirectory() → résultat dans une queue.Queue → réponse JSON au frontend. Le tout dans le même process, sans subprocess.

SESSION MAI 2026 (1) Auto-extinction — le serveur qui ne mourrait pas Fix

Problème rapporté : après avoir fermé l'onglet du navigateur, le processus DerushTool.exe restait actif dans le gestionnaire des tâches — indéfiniment. Gênant pour les utilisateurs qui ne pensent pas à le tuer manuellement.

Pourquoi c'est difficile à détecter côté serveur : HTTP est un protocole sans état. Quand l'onglet se ferme, il n'envoie aucune notification au serveur. Le serveur ne sait tout simplement pas que personne ne l'écoute plus.

Solution : système de heartbeat

Le frontend envoie un POST /api/heartbeat toutes les 5 secondes tant que la page est ouverte. Un thread daemon côté serveur surveille la date du dernier heartbeat reçu. Si 12 secondes s'écoulent sans heartbeat, le serveur s'arrête. Un bouton ⏻ dans l'interface permet aussi un arrêt propre immédiat.

Le délai de 12 secondes (plutôt que 5) est intentionnel pour absorber les variations réseau et les courts moments où le navigateur est occupé.

SESSION MAI 2026 (1) Bug 403 — Paola ne pouvait pas rejoindre le projet Bug

Lors du premier vrai test multi-utilisateurs avec Paola, elle obtient une erreur 403 (Forbidden) quand elle essaie de rejoindre le projet avec sa clé d'invitation. Les logs confirment que la requête arrive bien au serveur PHP.

Investigation

Le PHP retourne 403 quand la clé de synchronisation dans la requête ne correspond pas à $SECRET_KEY dans le script PHP.

Cause trouvée

Le fichier PHP déployé sur sebastiendelahaye.be avait encore la valeur d'exemple $SECRET_KEY = 'CHANGE_MOI_ICI'. La config locale avait bien la vraie clé drift2026, mais le PHP n'avait jamais été mis à jour après le déploiement initial.

Fix

Mise à jour du fichier derush_sync.php avec $SECRET_KEY = 'drift2026' et redéploiement sur le serveur. Confirmé fonctionnel via un test curl de Sébastien.

SESSION MAI 2026 (1) Chemin des rushs — chaque collaborateur a son propre disque Feature

Une fois l'accès de Paola réglé, nouveau problème : elle pouvait voir la liste des clips mais pas les lire — aucun moyen de lui indiquer que ses rushs se trouvent dans E:\DRIFT_CLUB\ sur son propre PC, pas dans le chemin de l'admin.

Le design du chemin par utilisateur

Le chemin des rushs est stocké par utilisateur dans le projet (proj['users'][i]['root_path']), pas comme chemin global du projet. Chaque collaborateur configure le sien de façon indépendante. Quand le serveur doit streamer un fichier, il utilise le root_path de la session de l'utilisateur connecté.

UX : prompt au premier accès

Si un utilisateur entre dans un projet sans root_path configuré, une modale s'affiche automatiquement lui demandant de choisir le dossier. Il ne peut pas fermer cette modale sans valider un chemin (ou annuler explicitement). Ensuite, un bouton 📁 dans la barre latérale permet de modifier ce chemin à tout moment.

SESSION MAI 2026 (1) Bug — le bouton Parcourir ouvrait un nouvel onglet Bug

Quand Paola cliquait sur le bouton 📁 pour choisir son dossier, cela ouvrait un nouvel onglet dans le navigateur. Et quand elle recliquait, rien ne se passait. Le sélecteur de dossier natif Windows n'apparaissait jamais.

La cause, pas évidente : Pour ouvrir une fenêtre de sélection de fichier native, le serveur Python lançait un sous-process python -c "code tkinter...". En mode développement, sys.executable pointe sur l'interpréteur Python — c'est logique. Mais dans l'exe packagé par PyInstaller, sys.executable pointe sur DerushTool.exe lui-même. Donc le "sous-process" relançait une instance complète du logiciel, qui ouvrait automatiquement le navigateur sur localhost:8765 — d'où le nouvel onglet.

Fix : tkinter dans un thread, pas un subprocess

La solution est de garder tkinter dans le même process. Un thread séparé est lancé depuis le serveur (obligatoire car tkinter doit tourner sur le thread qui fait l'appel, et le handler HTTP tourne dans son propre thread). Le résultat du dialogue est passé au handler via une queue.Queue avec un timeout de 120 secondes.

SESSION MAI 2026 (1) Scan générique — "et si j'ai une autre caméra ?" Feature

La question a été posée directement : est-ce que le logiciel fonctionne si j'apporte un dossier de rushs filmé avec une caméra différente, dans une arborescence différente ? La réponse honnête était : "probablement pas très bien".

Ce qui était codé en dur

  • La détection du TC byte-reversal FX6 s'appliquait aux fichiers nommés DRIFT_*
  • Les métadonnées techniques (ISO, ouverture, etc.) n'étaient extraites que depuis le sidecar XML Sony
  • La structure de dossier J02.../IMAGE/FX6/... était implicitement attendue

Ce qui a été généralisé

La fonction _extract_tech_metadata() essaie maintenant une liste exhaustive de noms de tags ffprobe pour chaque champ (ISO, ouverture, focale, obturateur) — couvrant les conventions Sony, Canon, Nikon, Apple (QuickTime), et les tags EXIF génériques. Le premier tag non-vide trouvé gagne. Pour les caméras sans sidecar XML, les métadonnées techniques viennent de là.

La détection de caméra suit une priorité : sidecar XML Sony en premier, puis tags ffprobe, puis nom du dossier parent. Les structures de dossiers sont maintenant toutes acceptées — la profondeur est adaptative.

14 MAI 2026 · SOIR Navette J/K/L — lecture arrière sans support navigateur Feature

Les touches J/K/L sont la norme dans les logiciels de montage professionnels (Avid, Premiere, DaVinci). L accélère en avant (1×→2×→4×), K met en pause, J joue en arrière à vitesse croissante.

Le problème de la lecture arrière

L'API HTML5 video.playbackRate accepte des valeurs positives allant de 0.1 à 16 environ. Elle n'accepte pas de valeurs négatives. La lecture arrière n'est tout simplement pas supportée nativement dans les navigateurs.

La solution : simuler la lecture arrière avec requestAnimationFrame. À chaque frame animée, on calcule le temps écoulé depuis la frame précédente et on recule manuellement le currentTime de la vidéo du même montant (× la vitesse désirée). Le navigateur affiche chaque frame "en arrière" — c'est pas parfait en termes de fluidité, mais pour du dérushage c'est largement suffisant.

Deux états sont maintenus : _jklSpeed pour la vitesse courante et _jklRevRaf pour l'ID de la RAF en cours. Le nettoyage se fait dans doLogout() pour éviter des RAFs orphelines après déconnexion.

14 MAI 2026 · SOIR WebSocket — collaboration en temps réel sans bibliothèque Feature

L'objectif : quand Sébastien pose un marqueur, Paola le voit apparaître dans son panneau "Avis des autres" sans avoir à rafraîchir la page. Le polling toutes les 60 secondes existait déjà mais était trop lent pour une vraie collaboration synchronisée.

Pourquoi implémenter WebSocket manuellement ?

Le serveur est basé sur http.server.HTTPServer de la bibliothèque standard Python. WebSocket est un protocole distinct (RFC 6455) qui commence par un handshake HTTP puis "upgradeˮ la connexion. Aucune bibliothèque externe (type websockets) n'a été ajoutée pour ne pas alourdir le build.

Le handshake WebSocket est implémenté directement dans DerushHandler.do_GET : si le header Upgrade: websocket est présent, on bascule en mode WS. L'acceptation nécessite de calculer un hash SHA-1 de la clé client + une magic string RFC, encodé en base64.

Authentification du WebSocket

Contrainte browser : L'API JavaScript new WebSocket(url) ne permet pas d'ajouter des headers personnalisés (contrairement à fetch). Impossible d'envoyer un Authorization: Bearer token. La solution adoptée : passer le token comme paramètre URL (/ws?token=xxx).

Gestion des clients connectés

Un dictionnaire global _ws_clients associe chaque project_id à une liste de (socket, token). Quand une annotation est sauvegardée, _ws_broadcast() envoie un message JSON à tous les clients du même projet, en excluant l'expéditeur. Les clients déconnectés sont détectés (exception lors de l'envoi) et retirés de la liste.

Côté frontend, la reconnexion est automatique toutes les 6 secondes en cas de déconnexion.

14 MAI 2026 · SOIR Vue multiclips — comparer deux prises côte à côte Feature

Pour comparer deux prises d'un même plan ou deux angles de caméra, il faut pouvoir voir les deux vidéos simultanément avec leurs annotations. L'overlay "Comparer" occupe tout l'écran pour maximiser l'espace vidéo.

Design de la timeline dans chaque slot

Chaque slot a sa propre mini-timeline scrubable avec les marqueurs de tous les annotateurs du projet. Cela implique une subtilité : dans la vue compare, on n'affiche pas les notes de l'utilisateur courant seulement, mais bien l'agrégat de toutes les annotations pour avoir une vision complète.

Le problème d'alignement seek/markers

Un problème subtil : la timeline container a 10px de padding de chaque côté pour que la piste ne touche pas les bords. Les markers sont positionnés en pourcentage de la piste (sans les 10px de padding). Mais la fonction de seek calculait le pourcentage par rapport au container entier. Résultat : cliquer à l'endroit exact d'un marker seekait un peu à côté.

Fix : cmpSeek utilise le getBoundingClientRect() de la piste (l'élément intérieur), pas du container timeline.

Le mode Sync

Quand le mode Sync est actif, scrubber un slot déplace également l'autre. Pratique pour comparer deux prises du même plan frame par frame. L'implémentation est simple : dans updateCmpTc(slot), si sync est actif et que le slot est le maître (slot 0), on force currentTime de l'autre vidéo.

14 MAI 2026 · SOIR Permissions granulaires — admin, annotateur, lecteur Feature

Avant cette feature, il n'y avait que deux états : admin (gère les utilisateurs, peut tout faire) et non-admin (peut annoter). Le besoin d'un rôle "lecteur" est venu du fait que certains intervenants (directeur, client) doivent pouvoir voir les annotations sans pouvoir les modifier accidentellement.

Compatibilité avec l'existant

Le champ is_admin existait déjà dans les données utilisateurs. Plutôt que de tout casser, le nouveau champ role est additionnel. Si role est absent (anciens projets), il est déduit de is_admin : True → admin, False → annotateur. Les anciens projets continuent de fonctionner sans modification.

Ce que masque l'UI selon le rôle

  • Lecteur : le champ notes, l'input tags, le bouton de confirmation de marqueur, les boutons de rating (visuellement grisés), le bouton Sauvegarder — tout est masqué ou désactivé.
  • Non-admin (annotateur et lecteur) : le bouton de gestion des utilisateurs, le bouton rescanner — cachés.
14 MAI 2026 · NUIT Preview LUT — première tentative (WebGL) Feature

La preview LUT permet d'appliquer un fichier .cube (table de correspondance couleur 3D) sur la vidéo en temps réel, pour visualiser l'étalonnage prévu sans ouvrir DaVinci Resolve.

Pourquoi WebGL semblait la bonne approche

Une LUT 3D de taille 33×33×33 a 35 937 points de correspondance. L'appliquer pixel par pixel en JavaScript sur une vidéo 1920×1080 à 30fps représenterait environ 2 milliards d'opérations par seconde — trop lent. WebGL (le GPU) semblait la solution évidente : une texture 3D samplée par un fragment shader, c'est exactement ce pour quoi les GPUs sont conçus.

L'implémentation WebGL

Un canvas superposé à la vidéo. Un vertex shader qui dessine un quadrilatère plein écran. Un fragment shader qui lit chaque pixel de la vidéo (texture 2D), cherche la couleur correspondante dans la LUT (texture 3D), et l'écrit en sortie. Le tout tourne en boucle via requestAnimationFrame.

Résultat : image entièrement noire. Avec le son. La vidéo tourne, le canvas est visible, mais tout est noir.

Ce bug allait nous occuper pendant toute la session du 15 mai — trois tentatives pour comprendre la cause réelle.

15 MAI 2026 · DÉBUT DE SESSION Corrections de la vue Compare Fix

Problème 1 — Les clips n'étaient pas à la même hauteur

Les deux slots de la vue compare sont côte à côte dans une grille CSS. Chaque slot est un conteneur flex vertical : en-tête fixe → zone vidéo flexible → timeline fixe → panneau d'info. Le panneau d'info avait une hauteur variable selon la quantité d'annotations (jusqu'à 130px max).

La mécanique : les deux slots ont la même hauteur totale (grille CSS). Mais si le panneau d'info d'un slot fait 50px (peu d'annotations) et l'autre 100px (beaucoup), la zone vidéo "flexible" absorbe la différence — les deux zones vidéo n'ont pas la même hauteur. Les vidéos sont centrées dans leurs zones respectives, mais comme les zones sont de tailles différentes, elles semblent décalées verticalement.
Fix : Hauteur fixe de 90px sur le panneau d'info (avec scroll interne si le contenu dépasse). Les deux zones vidéo sont maintenant toujours identiques.

Problème 2 — La tête de lecture décalée par rapport aux markers

Après avoir cliqué sur un marker (qui seekait correctement), la tête de lecture apparaissait légèrement à droite de la position du marker. Ce décalage visuel disparaissait en 50ms.

Cause et fix : Une transition CSS left .05s linear avait été ajoutée sur la tête pour la rendre "fluide". Mais cela signifiait que la tête arrivait à sa nouvelle position avec 50ms de retard. Quand on seekait vers un marker situé à gauche de la position courante, la tête partait de la droite et se déplaçait vers la gauche — pendant 50ms elle était bien à droite du marker. Fix : supprimer la transition, la tête se place instantanément.

Demande UX — Markers plus gros et mieux espacés

Les markers dans la timeline compare (7px, à mi-hauteur de la barre de 32px) étaient trop petits et collés à la piste. La barre a été portée à 52px, la piste descendue à 40px du haut, les dots agrandis à 13px. Cela laisse 26px au-dessus de la piste pour les markers — un écart visuel clair entre les points de couleur et la barre de progression.

15 MAI 2026 Debug LUT — trois tentatives, une leçon WebGL Bug · 3 tentatives

La LUT restait noire sur l'exe malgré plusieurs corrections. Voici le chemin de pensée complet.

Tentative 1 — La boucle RAF qui mourait

Hypothèse : La boucle requestAnimationFrame s'arrêtait quand la vidéo était en pause (le code ne reschedulait que si la vidéo jouait). Le canvas restait visible mais noir (son état initial), couvrant la vidéo.

Tentative 2 — Format de texture incompatible

Hypothèse : La texture 3D était stockée en RGB32F (virgule flottante 32 bits). Le filtrage LINEAR sur ce format en WebGL2 nécessite l'extension optionnelle OES_texture_float_linear. Sans cette extension, le sampler retourne des zéros — c'est-à-dire du noir.

Fix appliqué : conversion de la LUT en Uint8Array + format RGB8, universellement supporté. La perte de précision (float → uint8) est négligeable pour de la preview. Build, test.

✗ Toujours noir. L'extension n'était peut-être pas le problème, ou il y en a un autre en plus.

Tentative 3 — Le vrai coupable : les drivers ANGLE sur Windows

Analyse finale : Chrome sur Windows utilise ANGLE (Almost Native Graphics Layer Engine) comme couche d'abstraction entre WebGL et DirectX. Certaines fonctionnalités WebGL2 — notamment les vertex shaders qui utilisent gl_VertexID sans vertex buffer associé, ou les tableaux constants dans le shader (const vec2[4] P = vec2[](...);) — peuvent échouer silencieusement dans certaines configurations ANGLE. Le shader "compile" sans erreur reportée mais produit des pixels noirs. Pas d'exception, pas de message d'erreur visible sans debug explicite.
La difficulté du diagnostic : WebGL ne lève pas d'exception quand un shader échoue à la compilation (à moins d'appeler explicitement gl.getShaderInfoLog()). Le code semblait correct, les textures semblaient uploadées, la boucle tournait — mais le draw call produisait silencieusement du noir.

Solution finale : abandonner WebGL pour Canvas 2D

Plutôt que de continuer à investiguer les spécificités ANGLE/driver, on a changé d'approche fondamentalement. Canvas 2D est 100% compatible sur tous les navigateurs, sans aucune dépendance aux drivers GPU :

  1. drawImage(video, 0, 0, w, h) — frame vidéo → canvas à résolution réduite (≈480px)
  2. getImageData() — lecture des pixels du canvas (GPU → CPU)
  3. Boucle par pixel : calcul de l'index dans la LUT (nearest-neighbour), lookup dans le tableau Float32, écriture de la couleur LUT
  4. putImageData() — pixels traités → canvas (CPU → GPU)
Performance : Pour une vidéo 1920×1080 scalée à 480px de large (soit 480×270 = ~130K pixels), la boucle CPU traite environ 130 000 pixels par frame. À 30fps, c'est ~4 millions d'opérations/seconde — très confortable pour V8. Le readback GPU→CPU (getImageData) est la vraie limite, estimée à 2-5ms par frame. Le résultat est fluide en pratique.
✓ Canvas 2D fonctionne immédiatement, preview LUT opérationnelle.

La leçon retenue

WebGL est puissant mais son comportement sur Windows via ANGLE est imprévisible pour des shaders non-standard. Pour un outil de preview (pas de rendu critique), Canvas 2D est préférable : plus lent mais 100% fiable. Le WebGL aurait été justifié pour de la LUT en pleine résolution temps réel — ce n'est pas le cas ici.

15 MAI 2026 Lire le TC d'un BWF — BEXT direct, sans ffprobe Architecture

Le chunk BEXT d'un fichier BWF contient un champ TimeReference (64 bits, little-endian) qui donne le nombre de samples depuis minuit. Combiné au sample rate, ça donne le TC en secondes : tc_in_sec = time_ref / sample_rate.

On a deux implémentations en cascade dans read_bwf_tc() :

  1. _read_bwf_bext_direct() — parse le RIFF/WAVE en Python pur, lit les chunks fmt, bext, data. Très rapide (~5ms par fichier).
  2. _read_bwf_tc_ffprobe() — fallback via ffprobe pour les fichiers W64 ou exotiques.

Au scan d'un dossier son, on indexe tous les WAV/BWF avec leur tc_in_sec, duration_sec, sample_rate. 211 fichiers BWF dans le tournage DRIFT_CLUB indexés en quelques secondes.

Pour matcher un clip à un BWF : on calcule tc_clip (HH:MM:SS:FF → secondes) et on cherche un BWF dont tc_bwf ≤ tc_clip ≤ tc_bwf + duration (avec une grace de quelques secondes pour la précision jam-sync).

15 MAI 2026 · APRÈS-MIDI GCC-PHAT et multi-chunk — quand l'enveloppe RMS ne suffit pas Architecture

Le user signale que "Affiner" donne des corrections fausses sur certains groupes : la correction proposée empire la sync au lieu de l'améliorer. L'enveloppe RMS 100Hz a une résolution de 10ms et un pic mou quand le signal est lisse → l'algo prend n'importe quel offset dans la zone "à peu près correcte".

GCC-PHAT (Generalized Cross-Correlation with Phase Transform)

Technique standard utilisée en localisation acoustique pour aligner deux micros captant la même scène avec des qualités/positions différentes.

  • Travaille sur audio brut PCM 8kHz (résolution 0.125ms — bien sous la frame)
  • Normalise la phase dans le domaine fréquentiel : ignore les différences de niveau et d'EQ entre micros
  • Pic beaucoup plus net que xcorr classique même en SNR mauvais
R = SIG * conj(REF)
R = R / (|R| + ε)          # PHAT weighting
cc = ifft(R, n=interp*n)   # interpolation par zero-padding fréquentiel
tau = argmax(|cc|) / (interp * fs)
Premier essai catastrophique : GCC-PHAT direct avec fenêtre ±30s sortait des pics au bord exact (-29.96s ou +29.96s) avec z-score énorme (~500). Faux pics : artefacts FFT quand le signal commun est faible. L'algo trouve un alignement très net... avec un offset complètement inventé.

Approche coarse-to-fine

  1. Passe 1 : xcorr d'enveloppe RMS pour estimation grossière à 10ms près (±30s)
  2. Passe 2 : GCC-PHAT dans ±1s autour de l'estimation grossière (résolution 0.03ms avec interp=8)
  3. Garde-fou anti-bord : si le tau colle à <50ms du bord ±1s, on rejette la passe fine et on garde l'estimation grossière

Multi-chunk avec vote majoritaire

Pour les cas où même le coarse était mou (audio lisse, ambiance), passage au multi-chunk :

  1. Découpage du clip et du segment BWF en chunks de 20s (ou 10s)
  2. GCC-PHAT indépendant sur chaque chunk → on obtient N taus
  3. Médiane des chunks dont le z-score est ≥ 4
  4. Fiabilité jugée sur le MAD (Median Absolute Deviation) — si les chunks divergent > 200ms, c'est unreliable
Avantage : insensible aux passages silencieux ou divergents — il suffit que 3 chunks captent les mêmes événements pour valider. L'affichage 8/9 chunks ±0ms est très lisible pour comprendre la fiabilité.

17 MAI 2026 Mini-loop des secondaires quand le primary se termine Bug

Après calage des groupes, le user remarque sur mc_3528df45 : "quand j'avance dans la timeline jusqu'à la fin de Clip0005, avril0040 fait une mini boucle sur quelques frames". Reproductible sur tous les groupes où le primary est plus court que les secondaires.

La mécanique : _mcCurrentGroupTime() dérive le temps du groupe T depuis le primary : T = primary.currentTime + primary.normOff. Quand le primary atteint sa fin, son currentTime plateau à duration - 0.04, donc T plateau. Mais le RAF ne stoppe pas la lecture des secondaires (HTML5 video joue tout seul), donc leur currentTime continue d'avancer. Toutes les secondes, _mcDriftCorrect voit l'écart, et rebobine la secondaire vers localT = T - normOff qui ne bouge plus. D'où la mini-boucle d'1 s en rond.

function _mcCurrentGroupTime() {
    const pri = v.angles[v.primaryIdx];
    const priT = (pri.vidEl.currentTime || 0) + pri.normOff;
    const priDur = pri.vidEl.duration || pri.duration || 0;
    if (v.playing && priDur > 0 && pri.vidEl.currentTime >= priDur - 0.1) {
        // primary fini → suivre l'angle in-range le plus avancé
        let bestT = priT;
        v.angles.forEach((a, i) => {
            if (i === v.primaryIdx || !a._inRange) return;
            const aT = (a.vidEl.currentTime || 0) + a.normOff;
            if (aT > bestT) bestT = aT;
        });
        return Math.max(0, Math.min(v.groupDur, bestT));
    }
    return Math.max(0, Math.min(v.groupDur, priT));
}

Décision : on garde uniquement ce qui marche de façon prévisible — le matching par TC source. Quand les deux caméras sont jam-syncées, c'est frame-accurate. Quand une caméra a un TC cassé (cf. la FS5 sur certains jours de DRIFT — J04, J07, J10, J11), aucune paire ne se forme, et c'est très bien comme ça : mieux vaut un trou explicite qu'un faux match silencieux qui pourrit le montage en aval.

Ce qui a été supprimé

  • Serveur : compute_sync_fingerprint, _fingerprint_segment, _extract_pcm_segment, _multi_chunk_align, _gcc_phat, _xcorr_offset, _xcorr_offset_with_stats, le cache SYNC_FINGERPRINTS_DIR, et les constantes _MC_RATE/AUDIO_RATE/MAX_DUR/MAX_LAG/MIN_SCORE/MIN_SAMPLES.
  • Endpoints : /multicam/refine, /multicam/manual_pair, /multicam/group_bwf_analyze, /multicam/group_bwf_offset. Le champ bwf_offset_override / bwf_id_override dans les groupes disparaît.
  • UI : le bouton 🎵 Affiner, le sélecteur de BWF candidats, les boutons de nudge BWF (◄ son / son ►), le 💾 BWF, le 🔍 Auto, le modal de couplage manuel, la phase « Extraction audio » de la barre de progression.

Ce qui reste

  • _tc_pair_lag(clip_a, clip_b) — une seule fonction : si les TCs se chevauchent (grace _MC_TC_GRACE = 5s), retourne tc_b - tc_a. Sinon None. Pas de BWF, pas d'analyse.
  • detect_multicam_groups réduit à : pairs → lag → greedy camera-constrained grouping → BFS. Sans phase fingerprint.
  • _bwf_candidates_for_clips + /multicam/group_bwf + /bwf_audio/<id> : conservés uniquement pour jouer le son ingé de référence dans le viewer multicam. Pas de calage automatique, pas d'override.
  • Le bouton 🔊 Son ingé dans la toolbar du viewer : toggle simple, mute les caméras et joue le BWF au tc_earliest - bwf.tc_in_sec.
  • Le nudge des clips secondaires reste, pour corriger à la main si jamais une paire TC-validée se révèle décalée (rare en pratique).

Pourquoi pas garder l'audio comme fallback ?

Tentation forte de garder une « méthode B » au cas où. Refusé pour deux raisons :

Faux positifs invisibles. L'audio est confortable quand ça marche, dangereux quand ça échoue silencieusement. Un faux match avec un score à 0.9 et un MAD à 80ms est indistinguable d'un vrai à l'œil — il faut écouter chaque paire pour vérifier. À 100+ paires par projet, ce n'est pas tenable.
Le TC est binaire et lisible. Soit deux clips se chevauchent en TC, soit ils ne se chevauchent pas. Pas d'ambiguïté, pas de zone grise. Les jours « cassés » sont identifiables (FS5 J04/J07/J10/J11) et tu peux assumer que rien ne sera détecté pour ces caméras-là sur ces jours — pas de surprise.
Pour DRIFT : sur les jours où le TC FS5 est OK, le pipeline retrouve les paires FS5↔FX6 instantanément et frame-accurate. Sur J04/J07/J10/J11, il faudra de toute façon caler à la main dans DaVinci — l'outil n'essaie même plus de proposer un calage hasardeux qu'on aurait à re-vérifier.

Bilan

Le code serveur perd ~500 lignes (toutes les fonctions audio + 4 endpoints), l'UI perd 5 boutons et 3 fonctions JS auxiliaires, la détection passe de plusieurs minutes à instantané. Le périmètre fonctionnel rétrécit, mais la confiance dans le résultat augmente — ce qui est exactement le bon arbitrage quand l'outil sert à préparer un montage qu'on devra livrer.

17 MAI 2026 · TARD Décodeur LTC pure Python — le pivot inverse Feature

Le matin même on a pivoté vers "TC-only pas d'audio" parce que les méthodes audio (xcorr d'enveloppe, GCC-PHAT, multi-chunk) étaient peu fiables. Le soir, Sébastien identifie le vrai problème : sur la FS5, le timecode n'est pas dans les métadonnées mais encodé en LTC sur une piste audio. Le BZZZZ caractéristique audible dans les proxys J07-J11 (faits par la caméra) est en fait du timecode lisible.

Le LTC, c'est quoi : Linear Timecode — signal audio biphase mark à 80×fps bits/s qui encode HH:MM:SS:FF en BCD avec un sync word. La multiprise du tournage l'émet en continu, toutes les caméras qui le reçoivent enregistrent le même TC à chaque instant. C'est le standard pro pour synchroniser plusieurs sources.

Implémentation

Le décodeur tient en ~100 lignes Python+numpy. Étapes :

  1. _ltc_extract_pcm : ffmpeg sort 8s d'audio canal L en int16 PCM
  2. Détection des zero crossings → intervalles entre transitions
  3. Long intervalle (~bit_period) = bit 0 ; deux courts (~bit_period/2) = bit 1
  4. Recherche du sync word 0011111111111101 dans le flux de bits
  5. Décodage BCD des champs HH:MM:SS:FF

Stockage et utilisation

Le TC décodé est stocké dans clip['ltc_tc_in_sec'] dans le JSON projet. Un helper _clip_tc_seconds(clip) retourne le LTC en priorité, sinon fallback sur format.timecode (qui reste fiable pour les FX6 jam-syncées via SDI).

_tc_pair_lag et _temporal_candidate utilisent _clip_tc_seconds : du coup, sans rien changer à l'algo de matching, on a maintenant un TC frame-accurate pour les FS5. Résultat sur DRIFT : passage de 11 groupes détectés (juste FX6↔FX6) à des dizaines de paires FS5↔FX6 fiables.

UI

Un cadre 🎶 LTC ajouté dans la modale multicam, avant la détection. Boutons :

  • 🎶 Décoder LTC : décode tous les clips pas encore décodés
  • ↻ Re-décoder tout : force re-décodage (avec confirm)
  • Progress bar avec nom du clip en cours · compteur live "X avec LTC · Y sans"

Le décodage est persistant (stocké dans le JSON projet), à faire une seule fois par projet.

Validation sur 6 cas connus : Clip0002/0003 J02 (LTC), Clip0001 J02 (pas de LTC), J03 Clip0001, J07 caméra, J06 (pas de LTC). 6/6 corrects.
Endpoints ajoutés : POST /decode_ltc/start, GET /decode_ltc/status, GET /decode_ltc/summary. Pattern identique à /multicam/detect.
17 MAI 2026 · NUIT Bug du décodeur — 7 minutes d'écart sur Clip0037 Bug

Premier test du matching multicam après décodage LTC : faux positif évident. avril0065 (FX6) apparié avec Clip0037 (FS5), alors que la bonne paire est Clip0036. Sébastien me dit "Clip0037 n'a rien à voir, c'est une autre prise du même genre".

Diagnostic : les TC LTC stockés étaient faux. Pour valider, on décode Clip0037 à plusieurs offsets du PCM :

offset 0s  : LTC = 16:52:10  ==> début déduit = 16:52:10
offset 2s  : LTC = 16:59:11  ==> début déduit = 16:59:09
offset 5s  : LTC = 16:59:14  ==> début déduit = 16:59:09
offset 30s : LTC = 16:59:39  ==> début déduit = 16:59:09

À tous les offsets > 0, le décodeur donne le même TC de départ (16:59:09). À offset 0, il donne 16:52:10 — 7 minutes d'écart. Cause : le décodeur retournait le 1er sync word qu'il trouvait dans le PCM, mais sur les premières secondes du clip il peut y avoir du bruit qui ressemble accidentellement à du LTC (faux sync word avec TC bidon en BCD valide).

Le bug : 80 bits aléatoires peuvent par hasard contenir le pattern du sync word + des champs BCD valides (hh<24, mm<60, ss<60, ff<25). Sur une chaise qui grince ou du silence avec un peu de bruit, ça arrive de temps en temps.

Fix : validation par 3 frames consécutives + offset correction

  1. Après avoir trouvé un sync word valide, vérifier les 2 frames suivantes (80 bits chacune). Chaque frame doit avoir un TC = précédent + 1/fps (mod 24h). Si la séquence n'est pas continue → faux positif, on continue à chercher.
  2. Une fois un vrai run validé, calculer la position en samples du 1er sync valide dans le PCM (via une mapping bit_to_iv + zc[]). Soustraire cet offset au TC décodé → retourne le TC au début du PCM (= début du clip), pas au milieu.

Re-test sur les 6 cas connus : 6/6 toujours OK, et Clip0037 donne maintenant 16:59:09 (vrai TC). Plus de chevauchement avec avril0065 (16:52:04 → 16:55:10). Le faux positif disparaît. Sébastien valide : Clip0036 (vrai TC 16:52:46) est maintenant correctement associé avec avril0065, et Clip0037 est associé avec avril0066. Toutes les paires sont justes.

Leçon : un sync word seul ne suffit pas — toujours valider la cohérence sur N frames. Et toujours corriger l'offset entre la position du 1er sync valide et le début réel du PCM.

18 MAI 2026 Sémaphore et déduplication ffmpeg Fix

Après les fixes WebAudio, Sébastien voit encore des lags et "pléthore de processus ffmpeg dans le task manager". Diagnostic : à chaque hover sur un clip dans la sidebar, compute_strip lance 12 ffmpeg en parallèle (une par frame de la bande-contact). ThreadedHTTPServer accepte plusieurs requêtes simultanées sans limite. 20 clips hover rapide = 240 ffmpeg en simultané qui saturent CPU + RAM.

Fix

  1. Sémaphore globale : _ffmpeg_sem = BoundedSemaphore(min(8, CPU/2)). Tous les subprocess.run(ffmpeg...) du serveur passent par _ffmpeg_run() qui acquiert la sémaphore. Plafond global, jamais plus de N ffmpeg simultanés.
  2. Déduplication : _dedupe_compute(key, fn) avec un dict de threading.Event. Si la même requête arrive 2 fois (genre 2 GET /strip/clip0001), la 2e attend la 1ère au lieu de relancer 12 ffmpeg.
  3. compute_strip throttle interne : ThreadPoolExecutor(max_workers=3) au lieu de 12 threads. 12 frames mais en 4 batchs de 3.
  4. -analyzeduration 1M -probesize 5M -an sur toutes les commandes thumbnail : sans ça ffmpeg peut allouer >1 GB pour probe certains fichiers (MXF, GoPro HEVC) avant même de seek.
  5. compute_waveform_peaks numpy-isé : le struct.unpack + boucle Python pure créait un tuple de millions d'int (~300 MB à 1 GB pour clip 1h+). Avec np.frombuffer + reshape + mean vectorisé : ~10× moins de RAM, ~100× plus rapide.
Outil de debug utile : un script PowerShell watch_ffmpeg.ps1 qui liste les processus ffmpeg actifs avec RAM + ligne de commande, alerte quand un dépasse un seuil. Très précieux pour diagnostiquer quel call ffmpeg est responsable d'un pic.
18 MAI 2026 GoPro HEVC 5K — les LRV au secours Fix

Même avec la sémaphore, le watcher PowerShell montre un pic à 13 GB de RAM quand Sébastien scrolle sur les GoPro dans la sidebar. 4 juin 2026 · v0.3.9 Le cadre se cale sur l'image réelle, pas sur le fichier brut Fix

Retour de Sébastien sur l'overlay de cadrage : il aime le guide semi-transparent, mais certains rushs ont des bandes noires incrustées dans le fichier (master letterboxé). Quand il choisissait 4:3, le cadre rognait correctement à gauche/droite dans l'image réelle… mais en haut/bas il calait ses bords sur la bande noire, pas sur l'image.

Pourquoi : _videoDisplayRect() raisonnait sur la résolution brute de la vidéo (videoWidth × videoHeight), bandes noires comprises. Le rectangle de référence du cadre incluait donc le letterbox baké.

La détection des bandes

Nouvelle fonction _detectContentInsets() : on dessine la frame brute sur un petit canvas (200px), et on scanne depuis chaque bord la luminance MAX de chaque ligne/colonne. Une ligne dont le pixel le plus clair reste sous le seuil (24/255) est considérée comme une bande noire. Le « max » plutôt que la moyenne évite de prendre un objet sombre traversant une vraie ligne d'image pour une bande.

Convergence par le minimum : une seule frame peut tromper (fondu au noir, plan nuit). On accumule donc le minimum des insets vus au fil des frames (sur loadeddata, chaque seeked, et à l'activation d'un format). Les bandes ne peuvent que rétrécir quand une frame plus lumineuse révèle l'image — jamais grandir faussement. Le scrubbing fait converger vers la vraie taille des bandes.

Application

updateAspectOverlay() restreint d'abord son rectangle de référence à l'image réelle (insets retirés), puis pose les bandes letterbox/pillarbox comme avant. Résultat : un 4:3 sur un rush 2.39 baké délimite son haut/bas sur le bord interne des bandes noires — l'image réelle. Guide semi-transparent inchangé, détection 100 % client-side (aucun readback serveur, aucun job par clip).

Garde-fou : seuil à 24 = quasi pur noir. Un ciel sombre réel a presque toujours un pixel au-dessus de 24 sur sa ligne → pas pris pour une bande. Frame quasi entièrement noire → détection ignorée (fallback image pleine).

Méthode : un one-liner console envoyé à l'utilisateur a prouvé que les boîtes vidéo étaient au pixel près identiques (image 591 = 591). Donc le décalage n'était pas l'affichage. Un ffmpeg cropdetect a tranché : avril0005 → 1920×1012 (34px de noir haut + bas, matte 1.9:1 baké au tournage) ; Clip0003 (FS5) → 1280×720 plein cadre. Les FX6 du J01 ont un cache cinéma incrusté dans le fichier, pas les FS5 ni les FX6 du J02.

Détection FIABLE = côté serveur

La détection JS précédente (sur une frame isolée) était trompée par les plans sombres — c'est ce qui faisait déborder le cadre. Remplacée par detect_letterbox() : ffmpeg cropdetect sur 80 frames (s'accumule, robuste au plan sombre), résultat caché par clip (letterbox_cache.json), exposé via GET /letterbox/<clip_id>.

Crop via object-view-box

Côté client, _applyLetterbox() récupère les insets et pose video.style.objectViewBox = inset(…) : la propriété CSS recadre la source sur la zone non-noire, puis object-fit:contain l'ajuste → l'image remplit la boîte sans les bandes. Appliqué au lecteur, au comparateur et au multi-cam. Résultat : une FX6 mattée s'affiche à la même hauteur qu'une FS5 plein cadre.

Cohérence : _contentInsets est maintenant alimenté uniquement par le serveur (source unique fiable), et le cadre/format calcule sur le ratio du contenu (contain) → il se pose exactement sur la vidéo recadrée. Leçon retenue : sur un doute géométrique, mesurer (ffprobe/cropdetect/getBoundingClientRect) avant de toucher au CSS.
26 juillet 2026 · v0.3.10 Timeline + marqueurs visibles en plein écran Fix

En plein écran (bouton ⤢), la timeline et ses marqueurs disparaissaient complètement — on ne voyait plus que la vidéo brute, sans aucun repère.

Cause : toggleFullscreen() appelait requestFullscreen() sur #videoWrapper, qui ne contient que la vidéo et ses canvases (dessin, LUT, cadre). La barre de transport .player-controls et la .timeline-bar sont des siblings en dehors de cet élément dans le DOM — le navigateur ne fullscreen que l'élément ciblé et ses descendants, donc elles restaient hors-champ.

Fix : nouveau conteneur .player-fs-wrap (#playerFsWrap) qui englobe .player-area + .player-controls + .timeline-bar (mais pas .notes-panel, qui reste hors du plein écran — pas utile ici). toggleFullscreen() cible ce nouveau wrapper. La vidéo garde son flex:1 donc elle occupe tout l'espace restant au-dessus des contrôles et de la timeline.

Au passage, le raccourci F pour le plein écran était déjà documenté dans le guide utilisateur mais jamais câblé dans le code — ajouté au handler clavier global.

26 juillet 2026 La sauvegarde auto fonctionne-t-elle hors-ligne ? Doc

Question posée par Sébastien, sans certitude évidente vu qu'il y a deux mécanismes de sauvegarde distincts dans Derush Tool (local + cloud).

26 juillet 2026 · v0.3.11 428 clips perdus en un clic — incident réel + garde-fou Bug critique

Sébastien a rebranché son disque externe de rushs, qui a changé de lettre (D: → E:). Il a mis à jour le chemin dans l'app puis relancé un scan — et la liste de clips du projet est passée de 428 à 0, alors que les fichiers étaient bien là.

Diagnostic (mesuré, pas deviné) : les backups versionnés du projet montrent 428 clips à 10:29:31, puis 0 à 10:29:34 — trois secondes plus tard. Un vrai scan de ce dossier prend 64 secondes (mesuré en relançant scan_media_folder() directement). Trois secondes = un scan qui a échoué instantanément sur un chemin invalide, quasi certainement l'ancien D:\DRIFT_CLUB resté dans proj['root_path'] (un champ distinct du root_path par utilisateur, jamais mis à jour par le flow de changement de chemin).
Bonne nouvelle en creusant : les notes, marqueurs, groupes multicam et clips audio référencent les clips par id mais vivent dans des dicts séparés de clips[] — vider clips[] ne détruit aucune annotation, ça les rend juste invisibles (plus rien dans la sidebar). Récupération : restauration de clips[] depuis le dernier backup versionné d'avant l'incident, correction de root_path sur la lettre réelle actuelle.

La vraie faille : aucun garde-fou côté serveur

POST /api/project/<pid>/scan faisait proj['clips'] = scan_media_folder(...) sans jamais vérifier si le résultat avait un sens. Un chemin momentanément invalide (disque pas encore monté, lettre changée, faute de frappe) écrase silencieusement une liste de clips partagée par toute l'équipe — ce n'est même pas un champ per-user, une erreur d'un seul admin efface tout le monde.

Fix : si le projet a déjà des clips et que le nouveau scan en trouve moins de la moitié, le serveur refuse (HTTP 409, rien n'est sauvegardé) avec un message explicite. Un flag force:true permet de confirmer un vidage volontaire assumé. Le bouton 🔄 affiche l'avertissement en toast et transforme un second clic dans les 15 secondes en confirmation — délibérément pas de confirm() natif, pour ne pas retomber dans le bug de focus Electron déjà réglé ailleurs (voir la saga textarea plus haut dans ce journal).

Question ouverte : pourquoi le root_path de la session n'était-il pas à jour au moment précis de ce scan ? Plusieurs chemins de mise à jour existent (modale dédiée, édition admin) sans garantie qu'ils synchronisent tous SESSIONS[token]['root_path'] de la même façon. Le garde-fou protège contre la conséquence quel que soit le déclencheur exact — mais la cause précise mériterait d'être creusée si l'avertissement se redéclenche sans raison apparente.
26 juillet 2026 · v0.3.12 Reprise de la position de lecture par clip Feature

Demande de Sébastien : quand on est à un endroit précis de la timeline d'un clip, qu'on va voir un autre clip, puis qu'on revient sur le premier, il voulait retomber pile où il avait laissé la lecture — au lieu de repartir de 0 à chaque fois. Et le même comportement dans le comparateur et pour les clips synchronisés (groupes multicam).

Implémentation : une mémoire en RAM par clip.id (_clipResumeTime, déclarée dans js/audio-bwf.js — accessible partout grâce au scope global partagé entre les modules JS). selectClip() sauvegarde la position avant de changer de clip et la restaure au loadedmetadata du suivant. Même principe dans loadCmpClip() (comparateur, par slot). Pour le viewer multicam, comme un « groupe » n'a pas d'identité de clip unique, une seconde map _mcGroupResumeTime retient le temps-groupe (group.id → secondes), sauvegardée à la fermeture du viewer et réappliquée à la réouverture.
Cas particulier — bascule d'angle (swapToAngle) : ce mécanisme existait déjà et calcule explicitement le nouvel instant via les offsets du groupe (pour rester sur le même moment, pas la dernière position vue sur cet angle précis). Il continue de gagner sur la reprise générique — l'ordre d'attache des listeners loadedmetadata fait que son propre calcul s'applique en dernier.

Pas de persistance disque : la mémoire repart de zéro à chaque relance de l'app, ce qui correspond à la demande initiale (navigation dans une même session de travail).

26 juillet 2026 · v0.3.13 Comparateur : deux bugs de reprise + miniatures dans le sélecteur Bug

Retour de Sébastien après test de la reprise de position (v0.3.12) : « ça fonctionne, mais dans Comparer si je bouge à un endroit de la timeline et que je quitte, ça mémorise bien — par contre si je rouvre Comparer avec d'autres clips qui commencent au début, la timeline retient l'endroit précédent (par exemple 3/4 du clip). » Deux bugs distincts derrière ce symptôme, plus une demande de confort.

Bug 1 — mauvaise source de vérité à l'ouverture : openCompare() charge le slot gauche avec le clip actif du lecteur principal, mais lisait sa position dans _clipResumeTime[activeClip.id] — qui ne contient la valeur à jour que si on a quitté ce clip récemment via selectClip(). Si on est resté sur le même clip en scrubant dans le lecteur principal, l'entrée de la map n'a jamais été rafraîchie : Comparer rouvre alors sur une ancienne position (celle d'une session Comparer précédente), pas sur la position réelle actuelle.
Fix : juste avant de charger le slot 0, openCompare() écrase explicitement l'entrée avec mainPlayer.currentTime — le comparateur reflète maintenant toujours l'instant réel du lecteur principal à l'ouverture, quel que soit l'historique.
Bug 2 — barre de progression figée : indépendant du premier, purement visuel. La barre #cmpProgN/le TC #cmpTcN ne se mettent à jour que sur l'event timeupdate de la <video> — qui ne refire pas forcément immédiatement si le nouveau clip démarre à 0 sans seek. Résultat : la barre restait visuellement à la position du clip précédent jusqu'à ce qu'on appuie sur play.
Fix : reset explicite de la barre/TC au chargement + appel direct à updateCmpTc() après le loadedmetadata, sans dépendre uniquement de l'event natif.

Miniatures dans le sélecteur de clips

Demande complémentaire : identifier les clips plus vite dans les menus déroulants du comparateur. Un <select> HTML natif ne peut pas afficher d'image dans ses options (limitation de tous les navigateurs, pas seulement Chromium) — remplacé par un combo custom (bouton + liste stylée) qui affiche une miniature par clip via l'endpoint déjà utilisé pour le panneau Angles. Le <select> d'origine reste dans le DOM, juste caché, pour ne rien casser du code existant qui lit sa .value.
